## 1. What Den is

Private, self-hosted chat + media app (PWA) for a closed friend circle. Invite-only, owner-hosted (VPS + Postgres + Cloudflare R2), $0 to Apple — iOS is served via installed PWA at **`den.ems-place.com`** (domain locked forever: future passkeys bind to it as rpID).

**Shipped:** auth (invite + password), friending, DMs + group chats, realtime text over WS, media messages (image/video/voice) with presigned R2 upload + server-side processing, per-chat gallery (masonry grid + voice archive) with booru-style tag search and batch tagging, web push (incl. iOS installed PWA — verified on hardware), message soft-delete with undo + multi-select, message replies + reactions, full PWA polish pass (design tokens, dark mode, back-gesture bridge, safe areas), nightly `pg_dump` → R2 backups.

**Deliberate non-goals:** public discovery, user search beyond friends, moderation/reporting/blocking, E2EE in v1 (honest model: owner can technically read the DB; E2EE is roadmap).

## 3. Architecture

```
[iOS PWA] [Android PWA] [Desktop browser]
      │ HTTPS (REST + presigned R2 URLs)   │ WSS (socket.io)
      ▼                                    ▼
[Caddy] ──► [Fastify API + socket.io] ──► [Postgres]
                 │        └──► [web-push → APNs/FCM]
                 ▼ (inline, post-upload-complete)
          [sharp / ffmpeg] ──► [R2 / MinIO]
```

Core flows:
- **Text:** client → WS `message.send` → persist → fanout to `chat:{id}` room → push to members with no live socket in that room.
- **Media:** `POST /media/uploads` (mints presigned PUT + creates the message row) → client PUTs bytes straight to R2 → `POST /media/:id/complete` → server HEAD-verifies + magic-number sniffs → fans out `message.new` (status `processing`) → inline processing → `media.ready`. **Media bytes never transit the API server.**
- **View media:** short-lived presigned GETs minted per request (`GET /media/:id/url`).
- **Reconnect:** client refetches via Query invalidation. Never replay missed WS frames — DB is truth, WS is a hint.

## 5. Data model

**Truth:** `server/src/db/schema.ts` + `server/drizzle/` migrations (never edit an applied migration; add new ones). Tables:

`users`, `auth_identities`, `webauthn_credentials`, `invite_codes`, `sessions`, `push_subscriptions`, `friendships`, `chats`, `chat_members`, `messages`, `media`, `tags`, `media_tags`, `message_reactions`, `embeds`, `vault_links`.

Modeling rules (locked):
- **DMs are 2-member chats with `is_group=false`** (`dm_key` = "minId:maxId" enforces pair uniqueness). Never special-case DMs — this is the future-calls branch point and nothing else.
- **Media belongs to a message; messages belong to a chat.** Gallery scoping and jump-to-message fall out of the join. `media.message_id` is NOT NULL: the message row is created at upload-mint time; WS fanout waits for complete. Abandoned uploads leave orphan processing rows (accepted; orphan sweep is roadmap).
- **A message may own SEVERAL media — that's an album** (docs/MEDIA_ATTACHMENTS.md §4.1). `media.message_id` has only a plain index, never a unique constraint, so this needed no migration; `Message.media` is a `MediaInfo[]` and album-ness is derived from `media.length > 1` everywhere. `messages.kind` stays the **first item's kind** — there is deliberately no `'album'` kind, so `messages_kind_check` and every kind-branching path (reply previews, search, edit eligibility) are untouched. One send = one message = one push, and reply/react/delete/select address the album as a unit.
- **Sensitive media (`nsfw`/`spoiler`) is tags, not schema** (docs/MEDIA_ATTACHMENTS.md D5). `SENSITIVE_TAGS` in `shared/src/tags.ts` are ordinary per-chat tags with ordinary shared-wiki permissions — any member may mark or unmark anyone's media, and they search like any other tag. `MediaInfo.sensitivity` is a **derived projection** of them (`sensitivityOf()`, `nsfw` wins over `spoiler`), never a stored column. Clients blur on that field alone and must never string-match tag names.
- **Tags are per-chat** (`UNIQUE (chat_id, name)`), normalized (see §10), shared-wiki permissions, `tagged_by` = attribution only, `usage_count` maintained in app code.
- **Soft deletes** (`deleted_at`) everywhere users can delete; every read path filters them. Hard wipe is a roadmap item requiring an explicit logged override.
- **Replies:** `messages.reply_to_message_id` (nullable self-FK); API attaches a denormalized `ReplyPreview` (`{id, senderId, kind, preview, deleted}`) so clients render quotes without a second fetch and survive target deletion.
- **Reactions:** one row per `(message_id, user_id, emoji)`; API returns aggregated `ReactionSummary[]` (`{emoji, count, mine}`). Arbitrary emoji ≤32 chars stored; `ReactionLimits.quickEmojis` is the quick palette.
- **Auth is provider-ready by design:** `auth_identities` + `webauthn_credentials` exist from migration 001 but **nothing writes to them yet**. Invites authorize, providers authenticate; match OAuth users on `(provider, provider_user_id)`, never email; a user always keeps ≥1 login method.
- **Message search** (migration 006, docs/MESSAGE_SEARCH.md): `pg_trgm` extension + `idx_messages_body_trgm` gin trigram index on `messages.body` — substring search (ILIKE), not tsvector FTS, so mixed-language/partial-word queries behave like Discord's search instead of a stemmer.
- **Message edit** (migration 007, docs/MESSAGE_EDIT.md): `messages.edited_at` (nullable timestamptz), set the first time a message's body is edited. Own messages with a non-empty body only (text + media captions — the edit only ever touches `body`, never `media`); no time limit. No index needed — the existing trigram index covers edited bodies automatically.
- **Voice waveforms** (migration 0007 SQL file, docs/VOICE_WAVEFORM.md): `media.waveform` (nullable jsonb) — 44 RMS peaks quantized 0–255, computed server-side at processing time. Voice only; null for image/video and for legacy voice rows until `scripts/backfill-waveform.ts` runs.
- **Delivery receipts** (migration 009, docs/RECEIPTS.md): `chat_members.last_delivered_message_id` (nullable bigint, no FK — mirrors `last_read_message_id`) is a true device-delivery watermark, distinct from the read watermark. Both are **guarded-monotonic writes** (`WHERE watermark IS NULL OR < :id`) — a stale/out-of-order caller can never move either backwards. Per-user, not per-device: one watermark per `(chat_id, user_id)` row, same as today's unread counts.
- **Embeds — framework + Instagram** (migration 010, docs/EMBEDS.md §4): `messages.kind` gains `'embed'`. `embeds` belongs to a message exactly as `media` does (`message_id` NOT NULL FK, one row per embed message): `provider` ('instagram'|'vault'|'klipy' — the last added by migration 014), `status` ('processing'|'ready'|'failed'), a provider-agnostic card snapshot (`title`/`subtitle`/`description`/`thumb_key`/`canonical_url`/`provider_ref`/`content_kind`), `action_type` ('external'|'read'|'portal'|'inline', defaults 'external'), `data` jsonb for provider extras. Same async lifecycle as media: `message.send` sniffs the body for a recognized URL (`shared/src/embeds.ts`'s `detectEmbedUrl`, also used by the composer's paste-detect chip) → mints a `'processing'` placeholder + `message.new` → resolves in the background → `embed.ready`. Resolvers live in `server/src/embeds/registry.ts`'s plain provider→resolver map — `instagram`, `vault`, and `klipy` (docs/GIFS.md). `klipy` is the one provider never reached by URL detection: the client picks a GIF, so `ctx.url` is null and the slug carries everything.
- **Chat Stage — Vault docs owned by a chat** (migration 012, docs/EMBEDS.md §6, Phase 4): `chat_vault_groups` maps a chat → the **Vault group** that owns its docs (one per chat, created lazily on first Stage use — joining a chat never provisions a group for chats that never use the Stage). `chat_vault_docs` pins docs to a chat's Stage: shared-wiki semantics like tags (any member adds/removes, `added_by` is attribution only), soft-deleted. **Removing a doc from the Stage never deletes the Vault document** — the group still owns it, which is the whole point of group ownership: docs survive any member leaving. Den mirrors chat membership → Vault group membership on four triggers (`server/src/embeds/vaultGroups.ts`); every Vault write is fire-and-forget with an idempotent `reconcileChatGroup` sweep as the backstop, so a Vault outage can never block a Den-side action like joining a chat.
- **User settings** (migration 013, docs/MEDIA_ATTACHMENTS.md §4.2/D11): `users.settings` jsonb NOT NULL DEFAULT `'{}'` — a single typed bag (`UserSettings` in `/shared`) rather than a column per preference, because the owner intends to keep adding settings for existing features. `PATCH /me` **whitelists and merges**: unknown keys are dropped, values are type-checked, and a partial patch never replaces the stored object (so an older client can't clobber a preference it doesn't know about). Reads always merge over `DEFAULT_USER_SETTINGS`, so a pre-migration row still yields a complete object. First and only jsonb bag in an otherwise strict schema — keep it flat and JSON-primitive.
- **GIF attachments — Klipy** (migration 014, docs/GIFS.md): no new table. `embeds_provider_check` gains `'klipy'` and `embeds_action_type_check` gains `'inline'` — the latter is a real semantic addition meaning *this card **is** the content, there is nothing to open*, which is what keeps `EmbedCard` from painting an external-link chip that would lie about where a tap goes. A GIF is an embed and **never** a `media` row, so gallery exclusion is structural rather than a filter every future query has to remember. `provider_ref` holds the **canonical** Klipy slug: search results append a per-response analytics suffix, and only the by-slug lookup reports the durable form, so the resolver overwrites what the client sent (`ResolvedEmbed.providerRef`). `data` carries `{width, height, mimeType}`; `thumb_key` is reused as the *content* key, because for a GIF the "thumb" is the item. **Bytes are snapshotted to R2 as animated WebP** — never hotlinked — so a provider shutdown costs new searches, not chat history (which is not hypothetical: Tenor's API was switched off mid-2026).

- **GIF favorites** (migration 015, docs/GIF_FAVORITES.md): `gif_favorites` — one row per (user, canonical slug), holding `provider`, `provider_ref` (canonical slug), `provider_item_id`, a server-derived `preview_url`, dimensions and title. **Nothing here is chat-scoped**: a favorite references a public provider id, not a Den object, so invariant 1 has nothing to guard and per-user isolation is the whole access-control story (tested directly in `gifs/favorites.test.ts`). ⚠️ **This table HARD-DELETES on unfavorite** — a deliberate carve-out from invariant 8, which governs *content* (messages, media, Stage docs) rather than per-user toggle edges; `message_reactions`, `media_tags`, `friendships` and `vault_links` all already hard-delete, and a `deleted_at` here would make re-favoriting an un-delete. `provider_item_id` exists because a *search result* cannot be matched against a favorite by slug (search slugs carry a rotating suffix); the numeric id is stable across both canonicalization and token rotation (measured — docs/GIFS.md §12). It is nullable end to end, so a provider that stopped reporting ids would cost an unfilled star, never a dropped result.
- **Client aspect hints** (no migration, docs/MEDIA_ATTACHMENTS.md §4.6 + docs/GIFS.md D11): `CreateUploadItem` and the `gif` send intent both accept optional `width`/`height` so a `'processing'` row has a real aspect ratio for *other* members, instead of a fixed generic box that pops (and shoves the message list) when the bytes land. These are the only client-declared measurements Den accepts and they are **bounded, not trusted** — `server/src/aspectHint.ts` clamps the ratio to 1:5–5:1, normalizes to a nominal width so no pixel claim survives, and drops anything malformed; the server's own measurement (sharp/ffprobe, EXIF-orientation aware) overwrites it on success, and on failure the row is never rendered. This does **not** relax invariant 7, which governs what is fetched, stored and served — `completeUpload` still HEAD-verifies and sniffs every byte.
- **GIF favorites** (docs/GIF_FAVORITES.md §6): `GET /gifs/favorites` (keyset), `GET /gifs/favorites/keys` (unpaginated star state for all three surfaces at once), `POST /gifs/favorites` (`{slug}` only — the server calls Klipy to canonicalize *and* to derive every stored field, so no client URL is ever stored), `DELETE /gifs/favorites/:slug` (canonical slug). All `requireAuth`, all 503 when `gifsEnabled` is false. `EmbedInfo` gained `providerRef` so a chat GIF card has a handle to favorite with.

- **User settings** now carries `gifRating` (`'g'|'pg'|'pg-13'|'r'|'off'`, default `'pg-13'`) alongside `galleryShowSensitive` — no migration, which is the `users.settings` bag doing exactly the job it was added for. `PATCH /me`'s whitelist gained an **enum check** (`SETTINGS_ENUMS`): `typeof` alone can't police a union-typed setting, so every arbitrary string was passing until this landed. Any future union-valued key must be listed there the same day.
- **Vault account linking** (migration 011, docs/EMBEDS.md §5): `vault_links` — one row per Den user (`user_id` PK/FK), Den as an *outbound* OAuth 2.0 client of Vault (PKCE-S256, scope `vault.documents`). `access_token_enc`/`refresh_token_enc` are AES-256-GCM ciphertext (`server/src/integrations/crypto.ts`, key derived from `VAULT_TOKEN_ENC_KEY`) — never sent to the client, never logged. Distinct from `auth_identities`/roadmap #2 (Den's own future login OAuth); routes live under `/integrations/vault/*`, never `/auth/oauth/*`.

## 7. WS protocol

Envelope (LOCKED): `{type, payload, ts, reqId?}` — `shared/src/ws.ts`. One connection per client, session-cookie handshake. Rooms: `chat:{id}` (message-scoped fanout) and `user:{id}` (chat-agnostic notices). Heartbeat ~25s (proxy timeouts).

Current types: `hello ping pong error` · `message.send message.new` · `chat.created` · `friend.request friend.accepted` · `media.ready` · `tag.added tag.removed` (emitted since Stage 5; the client handler was invalidate-only until docs/MEDIA_ATTACHMENTS.md §4.5 taught it to patch `media[].sensitivity` in place, so marking an old photo `nsfw` re-blurs it live for everyone) · `message.deleted message.restored` · `message.edited` · `reaction.added reaction.removed` · `delivered.ack` (client→server, batched, fire-and-forget) · `message.delivered message.read` (docs/RECEIPTS.md — room broadcasts, only on a real watermark advance) · `embed.ready` (docs/EMBEDS.md §4.2 — room broadcast, identical shape/reasoning to `media.ready`: the resolved card replaces the `'processing'` placeholder in place) · `presence.update` (client→server, fire-and-forget, docs/NOTIFICATIONS.md §2.1 — `{chatId|null, visible}`; membership-gated, never echoed, and read by exactly one consumer: push targeting).

**GIFs added no WS type** (docs/GIFS.md §6). `MessageSendPayload` gained an optional `gif: {slug, width?, height?}` intent instead — the "client sets an intent" half of docs/EMBEDS.md §4.3's mint path, designed from the start and unused until now. Overloading `message.send` rather than adding a route or a type means GIFs inherit optimistic send, `reqId` dedup, room fanout, push and unread counts with no parallel path to keep in sync. Only the slug is authoritative; the dimensions are a clamped cosmetic hint (§5).

Rules:
- New features add `type` values to the `WsType` registry — never a second envelope or side-channel.
- **`call.signal.*` / `call.state.*` prefixes are reserved** (guarded by `isReservedWsType`) for future calls.
- The `error` type goes to a single socket with `reqId` correlation, never to a room.
- Chat creation must join **all** members' live sockets to the new room, including the creator's (past bug).
- Client-side echo dedup: optimistic writes register a pending key (reqId for sends, `messageId:emoji:action` for reactions) consumed by the server's own echo; other users' frames always apply.

## 8. Media pipeline

- **Ceilings at mint time** (images 25MB, video 500MB, voice 20MB — `MediaLimits`), **verification at complete time** (R2 HEAD size + `file-type` magic-number sniff; mislabeled kind → 400 before processing). Never trust client mime/size.
- **Images:** sharp — `.rotate()` (EXIF orientation) then re-encode WebP **without metadata → EXIF/GPS stripped**, + 400px WebP thumb. HEIC decodes via sharp's bundled libvips.
- **Video:** ffmpeg poster frame (t=0.5s) + ffprobe dims/duration. No transcode — original stored as-is.
- **Voice:** ffmpeg → mono 48kHz AAC/m4a, always. One storage format; no playback-time format detection. Inputs vary by platform (iOS `audio/mp4`, Chrome `audio/webm;codecs=opus`) — both valid. A second ffmpeg pass decodes the m4a to 8kHz mono PCM for stored waveform peaks (`media.waveform`, docs/VOICE_WAVEFORM.md) — best-effort, null on failure.
- Image/voice raw originals are deleted from R2 after re-encode; video keeps its original.
- Keys: `media/{chatId}/{mediaId}/orig.{ext}` + `.../thumb.webp` (chat-prefixed for future export/deletion). Presigned GETs ≤1h.
- Failure flips `media.status='failed'` cleanly; the placeholder message stays.

## 9. Auth, sessions, push

- Invite codes: single-use, admin CLI (`npm run invite create`). Registration requires one.
- Sessions: random 256-bit token in httpOnly/Secure/SameSite=Lax cookie ↔ `sessions` row; logout deletes the row. Login is case-insensitive (citext), no username enumeration. Auth routes rate-limited 10/min.
- Push (rebuilt 2026-08-23, `docs/NOTIFICATIONS.md`): VAPID keys in env. Notify every member **except the sender and anyone whose socket reports it is looking at that chat right now** (`realtime/presence.ts`). ⚠️ The old rule — "no live socket in the chat's room" — was wrong and is the bug this pass exists to fix: every socket joins *every* one of its user's rooms, so that test only ever meant "has a socket somewhere", and a backgrounded PWA silenced its own notifications. A socket with no presence report counts as not-watching: this fails toward notifying.
- Payload `{chatId, chatName, senderName, preview, url}`, built **per recipient** — `chatName` is null for a DM (the SW titles it with the sender) and excludes the recipient from an unnamed group's fallback name. `url` is `/?chat=<id>`, a consume-once launch parameter, not a route.
- Delivery: `urgency: 'high'` + 12h TTL + `topic: chat-{id}` (push-service-side coalescing, mirroring the SW's `tag`). `renotify: true` so a replaced notification still alerts. Non-404/410 failures are logged, never swallowed.
- Subscriptions self-heal: a `pushsubscriptionchange` handler in the SW, plus a gestureless re-POST of the existing subscription at every app start. Delete rows on 404/410 (iOS reinstall churn).
- App badge = chats with something waiting; written by the client from `['chats']` and by the SW from its notification count (same unit, two writers).
- iOS: push requires installed PWA (≥16.4) + user-gesture permission prompt ("Enable notifications" button, never auto-prompt). The startup re-sync is structurally incapable of prompting — it only re-registers a subscription that already exists.

## 10. Tags & gallery

- Normalization (`shared/src/tags.ts`, client AND server): trim → lowercase → spaces→hyphens → collapse; charset `[a-z0-9_-]`; ≤64 chars. Hinted live in the UI, never silent.
- **Reserved names `nsfw` and `spoiler`** (`SENSITIVE_TAGS`) make media render blurred behind a tap-to-reveal pill. Nothing about them is special-cased in the tag layer — same table, same registry, same shared-wiki permissions, same search (`nsfw`, `-nsfw`). Only `sensitivityOf()` reads them specially, and its result rides on `MediaInfo.sensitivity`. ⚠️ Blur is cosmetic, **not** a security control: real thumbnail bytes still reach every member (docs/MEDIA_ATTACHMENTS.md D10).
- Query language: booru AND + negation only (`beach -screenshots`). Parser in `shared/src/tags.ts`; an unresolvable positive tag short-circuits to an empty page.
- Gallery SQL lives in `server/src/media/gallery.ts` (raw SQL allowed there by convention). Positive matching = one `EXISTS` per required tag (the documented `unnest(...)::bigint[]` form fights the driver — see archive §15 2026-07-20).
- Gallery partitions into **Media** (masonry grid, `kind=visual` = image|video, All/Images/Videos sub-filter) and **Voice** (chat-skinned bubble list — never thumbnails). Day-level date sections in both. Multi-select batch tagging in Media only (client-side `Promise.allSettled` over per-media endpoints — no batch API).

## 11. Frontend architecture

- **Navigation:** no router. `App.tsx` holds a discriminated-union `View`; mobile (≤768px, `useIsMobile`) renders one full-screen view + bottom tabs (Chats/Gallery/Profile); desktop renders an icon rail + dual-pane Chats (360px list + chat). Profile is a landing page (identity card + a `Settings ›` row); **Settings** is its own pushed view whose `parentOf` is `profile`, and it owns Media & privacy, Notifications, Connections (Vault) and Debug tools. Crossing the breakpoint remounts `ChatView` — per-chat state that must survive lives in App-level ref caches (see `draftCacheRef`; copy that pattern).
- **Back gesture:** `lib/backStack.tsx` — single re-armed history trap; overlays/selection modes register LIFO handlers and close first; views unwind via `parentOf`; root back is inert (never exits the PWA). Every new overlay must register (`useBackHandler`).
- **Escape = desktop's back gesture**, on the same LIFO stack: `useBackHandler(active, onBack, { escape: true })`. Opt-in, and honoured **only while that layer is topmost** — so a viewer over a grid sheet closes itself and leaves the sheet, and Escape can never reach past an overlay to close something behind it. Overlays, modals and selection modes opt in; plain views deliberately don't (Escape shouldn't fling you out of a chat mid-sentence). `MediaViewer` additionally binds ←/→ to prev/next, ignored while a text field has focus (its own `TagEditor` lives inside it).
- **Realtime layer:** `lib/realtime.tsx` writes WS frames into the Query cache; optimistic sends reconcile via reqId. **Reconnect *and* resume both mean "resync"** — `RealtimeProvider` listens for `visibilitychange`/`online` as well as the socket's `connect`, and all three run the same `resync()`. Resync is **not** a blanket `invalidateQueries(['messages'])`: on an infinite query that refetches every loaded page sequentially, so the open chat instead gets one newest-page fetch merged by `lib/messageSync.ts`, and chats that aren't on screen are only marked stale. `useMessages` therefore turns **off** `refetchOnWindowFocus`/`refetchOnReconnect` — resume is owned here, deliberately, in one place. Resume also **verifies the socket rather than trusting `socket.connected`** (`reviveSocket` in `lib/socket.ts`): a frozen page's timers don't run, so engine.io can't notice a dead peer until long after the user is looking at the screen. The provider additionally owns **presence** (`setActiveChat`, docs/NOTIFICATIONS.md §2.1): `ChatView` reports which chat is on screen, and this layer re-reports it on both visibility edges and on every reconnect, because presence lives on the socket and a new socket starts blank.
- **Chat rendering:** `lib/messageGroups.ts` groups into runs (same sender, 5min) → blocks → optional media stacks; run-position-aware bubble corners; date/time dividers derived from loaded pages. Bare media renders bubble-less. **Captioned media is one card** (docs/MEDIA_ATTACHMENTS.md §5.3): a single `overflow-hidden` container, media flush to the top and sides with the container supplying the radius, caption strip beneath in the bubble fill — not a bare image with an independent bubble under it. Card width = the media's display width (no minimum, no gutters; a narrow portrait wraps its caption narrow, accepted).
- **Two multi-media layouts, and the difference is meaningful:** a **fan** (`MediaStack`) is several *separate* sends grouped by proximity (the legacy adjacency heuristic, unchanged); a **mosaic** (`AlbumCard`) is one album — one message carrying N media, composed and sent together. Multi-media messages are excluded from `isStackable` so an album never merges into a fan. Mosaic is a fixed-width card of square `object-cover` tiles (2/3/4/5/6 layouts, `+N` on the sixth past 6).
- **Viewer filmstrip** (`MediaFilmstrip`, docs/GALLERY_FILMSTRIP.md): the bottom rail in both viewer surfaces (gallery result set, and chat albums). Slots are a **fixed grid**; the active/neighbour enlargement is a paint-only `transform`, so centring and hit targets never move — that separation is what any future drag-to-seek must preserve. The unloaded tail renders as ghost slots sized by `totalCount`, and scrolling the rail pages more in, which is what keeps keyset pagination workable without an offset-jump API. Windowed rendering (fixed slot width ⇒ trivial arithmetic, no dependency).
- **GIF picker** (`GifPanel.tsx`, docs/GIFS.md §8): tapping the composer's GIF button **replaces the composer row** rather than expanding a sheet above it, and that swap is load-bearing twice over — the textarea carries the draft (`draftCacheRef`, which survives the mobile/desktop remount), paste-detect and edit mode; and three rounds of keyboard work (§14, 2026-08-13) hang off the composer's own bottom padding, so a panel floating above a live composer would give one bottom offset two owners. It stays *inside* the composer `<form>` to inherit `--kb-inset`/safe-area, which means anything in it that can submit must `preventDefault` Enter — the search field does, after it was found sending the user's draft from behind the open picker. Results use the gallery's shortest-column masonry (`lib/masonry.ts`); a row-based grid was tried first and rejected because one portrait GIF sets its row's height and every landscape tile beside it sits in dead space. Registers on `backStack` like every overlay. **Favorites** (docs/GIF_FAVORITES.md §8) add a second tab to this panel and a press-and-hold popover on each tile — ⚠️ and that hold is the one gesture in Den where getting it wrong *sends a message*, since a tile's click sends immediately. Its decisions therefore live in a pure, unit-tested state machine (`lib/pressGesture.ts`) rather than in component refs. In chat the star joins the existing hover bar (`MessageActions`) and focus menu rather than overlaying the GIF, so a GIF bubble keeps exactly one hover affordance. **KLIPY attribution** (docs/GIFS.md §9) is satisfied on all three counts their guideline names — the `Search KLIPY` placeholder (the only REQUIRED one), the "Powered by KLIPY" logo in the panel footer, and a watermark on sent GIF cards — using their official SVGs self-hosted in `app/src/assets/klipy/`, never recolored, swapped by `prefers-color-scheme`. ⚠️ The sent-card watermark is a **CSS overlay in `EmbedCard`, never baked into the stored WebP**: that object is permanent and shared, so a baked mark could never be removed and a rebrand would strand every GIF ever sent with a dead logo.
- **Sensitive-media blur:** `SensitiveOverlay` is the single blur treatment everywhere (chat, mosaic tiles, grid sheet, viewer, gallery, composer tray); `lib/sensitivity.tsx` holds the app-session reveal set. Blur is **per item** (a clean tile is never hidden by a marked sibling), but revealing any blurred tile of an album reveals all of them. Reveal state is deliberately in-memory and shared between chat and gallery — never persisted (iOS storage eviction would make it feel arbitrary; §12).
- **Gestures (all hand-rolled Pointer Events — no gesture/animation library, ever):** long-press (500ms/10px) → focus menu or selection mode; swipe-to-reply (toward-center, 12px engage / 56px fire); double-tap-to-react (~250ms single-tap delay, accepted cost); MediaViewer is split two ways (docs/GALLERY_FILMSTRIP.md §5.6): the **stage** owns navigation and swipe-to-close as a real carousel — the whole track moves, the neighbour slides in, a committed swipe finishes the travel — tracked on window listeners so the image's own handlers still fire; the **image** owns pinch/double-tap/pan-while-zoomed, and the stage stands down while zoomed. Video goes through the same stage path (no duplicate implementation) with a 56px native-controls exclusion. Selection mode and viewers are mutually exclusive.
- **Stacking-context lesson (hard-won, 3 debugging rounds):** portalled fixed overlays MUST set an explicit `zIndex` on the outermost wrapper — `position:fixed` + `z-index:auto` paints at the parent's layer and loses to any positioned sibling regardless of inner z-values. See archive §15 2026-07-22.
- **Design tokens only** (`index.css` `@theme`): surface/surface-raised/surface-sunken, text-primary/secondary/muted, border, accent/accent-hover, radius + shadow scales. Dark mode via `prefers-color-scheme`. Exception precedent: accent-text-on-dark and error colors stay literal.
- **SW/update discipline:** custom `sw.ts`; API + WS never cached; `registration.update()` on foreground + auto-reload on `controllerchange`. The SW also owns notification behaviour (docs/NOTIFICATIONS.md) — and one rule there is worth carrying elsewhere: **a tapped notification messages a running client, it never navigates it.** `client.navigate()` is a real navigation even to the URL already loaded, so it reloads the PWA and takes the draft, staged attachments and scroll position with it.

## 12. Platform reality (iOS is load-bearing, dev is Android)

Dev device: Samsung, with the PWA installable in **both Chrome and Firefox** — always establish which one a dev-device report came from before diagnosing anything platform-shaped, because Gecko ≠ Chromium and they diverged sharply here once already (§14 2026-08-13: Firefox has no VirtualKeyboard API, no `env(keyboard-inset-height)`, and reports the soft keyboard as one viewport jump ~593ms after focus instead of tracking it; owner moved to Chrome for daily use as a result). Most users: iPhone. Anything likely to diverge on iOS Safari/installed-PWA gets ⚠️-flagged for the standing real-device gate — never silently called done. Known load-bearing quirks:

- `100dvh` not `100vh`; `env(safe-area-inset-*)` on bars/headers; `touch-action: manipulation` on controls; `overscroll-behavior: none`.
- MediaRecorder yields `audio/mp4` (iOS) vs `webm/opus` (Chrome); audio playback and AudioContext need a user gesture (`audio.play()` must be called synchronously in the gesture, before async work); `OfflineAudioContext` decode needs no gesture.
- Push: installed-PWA-only, gesture-gated prompt, subscription churn on reinstall. **Unverified after the 2026-08-23 rebuild (docs/NOTIFICATIONS.md §9):** `renotify` on WebKit (the burst case — does message 2 of a run actually alert?); `getNotifications()`-based dismissal in an installed PWA (historically unreliable); `setAppBadge` from the SW vs. from the page; whether `notificationclick`'s `clients.matchAll` finds a suspended-but-alive PWA client (that branch decides fast in-app open vs. cold `openWindow`). iOS should now receive **more** notifications than before, since it suspends hardest — confirm that's what happens and that it isn't duplicative.
- iOS may evict PWA origin storage after weeks — the app must cold-start cleanly from the API with zero local state (hard invariant: server is truth).
- Edge-swipe-back vs. rightward gestures (swipe-to-reply near the left edge) — flagged, unverified. The 2026-08-23 rewrite adds a second thing to watch here: the gesture now calls `setPointerCapture` once it engages, so if WebKit's edge-swipe still wins the touch it should surface as a `pointercancel` (handled — the block snaps back) rather than a stranded bubble.
- **Chat gesture pass, 2026-08-23 (§14), all unverified on iOS:** `overscroll-behavior-y: contain` on the message scroller — Safari 16+ only, and iOS rubber-band is a different mechanism from Chrome's pull-to-refresh, so confirm a pull past the top of history neither reloads nor feels dead. The focus menu's live re-measure is the bigger one: it is driven by `visualViewport` resize/scroll on iOS (the layout viewport never resizes for the keyboard there), so long-press a bubble *with the keyboard up* and confirm the lifted clone lands on the real bubble's final position rather than drifting — this was the reported Android bug and iOS reaches the same code by a different signal.
- Known-unbuilt: `visualViewport` composer pinning against the iOS keyboard (code-complete, still awaiting the real-device gate — see §14 2026-07-23); skeleton loaders.
- **Staged attachments / blur (docs/MEDIA_ATTACHMENTS.md §5.7, all unverified on iOS):** `filter: blur()` over several images in a scrolling list (perf on older iPhones); HEIC object-URL previews in the composer tray (Safari decodes them, Chrome doesn't — so the `onerror` fallback tile is precisely the path that should *not* fire on iOS); the tray's interaction with `--kb-inset` while the keyboard is open, and the attachment-sheet-vs-keyboard handoff; multi-select through the iOS photo picker via `<input multiple>`.
- **GIFs (docs/GIFS.md §13, all unverified on iOS):** animated-WebP decode in an installed PWA; several looping GIFs in a scrolling list (perf on older iPhones — same class as the blur-perf flag above); the picker↔keyboard handoff and the panel's `--kb-inset` behaviour now that it owns the bottom edge; the composer's leading slot at 360px, which now holds attach **and** GIF alongside the input. Note the aspect-hint path (§5) is one of the rare places iOS should behave *better*: Safari decodes HEIC, so it will produce a hint where Chrome cannot.
- Real-device-verified so far (2026-07-21/22, prod): iOS push, iOS voice round-trip, install flow, Android PWA general pass. Still unverified on iOS: HEIC upload, cold-start session persistence, most touch-gesture feel, clipboard image paste (long-press → Paste with an image copied — `docs/IMAGE_PASTE.md`). Also needs a dev-device check: Android Samsung-keyboard clipboard-image paste; the 2026-08-13 keyboard re-pin (focus the composer at the bottom of a chat → newest message stays visible above the keyboard; scroll up into history, focus the composer → the view must *not* jump).
